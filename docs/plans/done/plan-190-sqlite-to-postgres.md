# SQLite → Postgres Database Migration Plan

**Goal:** Replace Tama's SQLite state store with Postgres as the sole backend, then remove SQLite entirely.
**Architecture:** Staged migration: (1) infra — sqlx pool, testcontainers, squashed v1 Postgres migration; (2) bootstrap config + pool wiring; (3) port the Config orchestrators and all 14 query modules **plus every other rusqlite-backed layer** domain-by-domain from sync rusqlite to async sqlx, converting all callers to await; (4) delete all SQLite machinery; (5) one-time `tama migrate` subcommand for data + bootstrap-config cutover.
**Tech Stack:** sqlx (postgres, runtime-tokio-rustls, time, migrate), testcontainers + testcontainers-modules, clap (new, CLI subcommands), toml_edit (new, bootstrap file write), existing `percent-encoding` (tama-core) and `url` (workspace) deps.

**Approved spec (from discussion, do not deviate):**
- Postgres is the ONLY backend — full SQLite removal, no fallback mode
- Runtime sqlx queries (`sqlx::query()` / `sqlx::query_as()` with explicit decoding) — NO compile-time `query!` macros, no `.sqlx` offline cache
- One squashed Postgres `v1` migration distilled from the 49 SQLite migrations; sqlx `Migrator` for all future versions
- `TIMESTAMPTZ` with `DEFAULT now()` replaces all TEXT ISO-8601 timestamps; decode as `time::OffsetDateTime` (sqlx `time` feature); API serialization to the frontend keeps emitting ISO-8601
- Identity columns: **`BIGINT GENERATED BY DEFAULT AS IDENTITY`** (not `ALWAYS` — `tama migrate` must insert explicit v2 ids so FKs line up; `BY DEFAULT` accepts explicit values and `setval`s the sequence afterwards)
- `PgPool` with `connect_lazy`; startup = **retry connectivity first** (exponential backoff 1s→30s cap, daemon stays alive), THEN run migrations; a genuinely failing migration (SQL/permission error) exits non-zero, an unreachable server keeps retrying. Distinguish the two by error kind, not by hoping.
- Type mapping: singleton `id BIGINT PRIMARY KEY CHECK (id = 1)` kept; `REAL` → `DOUBLE PRECISION`; int-bools → `BOOLEAN`; `INSERT OR REPLACE` → `ON CONFLICT ... DO UPDATE`; `INSERT OR IGNORE` → `ON CONFLICT ... DO NOTHING`; JSON `TEXT` columns (`reasoningLevels`, `health_check`, etc.) stay `TEXT`
- **Config architecture (revised post-review — the app config does NOT live in `config.toml`):** since v2.x, global config is stored in the DB (`Config::from_db()`/`to_db()`; `config.toml` was auto-migrated to `config.toml.migrated`). In v3 the app config lives in **Postgres**, and `config.toml` becomes a **bootstrap file containing ONLY a `[database]` section** (host/port/name/user/password). Bootstrap password supports `${VAR}` env resolution; if the env var is missing at startup, fail loudly (a new `resolve_env_var_ref_required` returning `Result` — the existing private `resolve_env_var_ref` in `crates/tama-core/src/config/types/proxy.rs` keeps its warn-and-continue semantics for OAuth). The config save API never touches the bootstrap file; the bootstrap file is written only by `tama migrate`.
- `Repository` + `Arc<Mutex<>>`, `Config::open_db()`, `ProxyState::open_db()`, and all `spawn_blocking` DB bridging are DELETED in the deletion task; callers await `&PgPool` directly
- Backup: `tama.db` dropped from archives; the manifest's models/backends lists are populated by querying **Postgres**; `ExtractResult.db_path` removed; global config is NOT in backups in v3 (documented — `pg_dump` is the DB backup path, see MIGRATION.md)
- Tests: testcontainers — one Postgres container per test binary (cached in a process-global OnceCell), each test gets a dedicated schema (created + dropped by a helper), pinned `postgres:16` image
- `tama migrate --sqlite <path> --db <postgres://url> [--password-env <NAME>] [--dry-run] [--force]`: one Postgres transaction, tables in FK-dependency order, explicit ids with `BY DEFAULT` identity + `setval(pg_get_serial_sequence(...))` after, refuses if target has data (or bootstrap config.toml exists) unless `--force`, skip-and-report (JSON file) for type-invalid rows, CREATES the bootstrap `config.toml` (with `config.toml.bak-<ts>` if a file exists) ONLY after the data transaction commits
- Breaking release: v3.0.0. A `docs/MIGRATION.md` v3.0.0 section (newest-first, follow the v2.0 section format) is part of this plan

### Task 1: sqlx + testcontainers infra, squashed v1 migration, v49 DDL fixture, migration tests

**Context:**
Stage 2 (infra part 2). The app still runs on SQLite for app config and data — this task wires in the NEW Postgres side. ### Task 3: Port the Config orchestrators — app config moves to Postgres

**Context:**
First domain port, and the trickiest: the global app config currently round-trips through SQLite via `Config::from_db()`/`to_db()` (`config/types/mod.rs:73,258`), built on `app_config_queries.rs` (the singleton-table CRUD incl. `seed_defaults` at `app_config_queries.rs:539`). `Config::load()` (`config/types/mod.rs`), `load_from`, `save`, and `Config::open_db()` (`config/resolve/mod.rs:631`) all take/hold a `rusqlite::Connection` or `&Path`. This task ports `app_config_queries.rs` AND the orchestration so **the app config is read from and saved to Postgres**. This is the cutover point for config: after this commit, a running dev instance reads config from Postgres (a fresh dev Postgres holds defaults until `tama migrate` copies real data — that is expected mid-migration; note it in the commit message). The legacy TOML→DB auto-migration in `config/loader.rs` is deleted here (v2 users are handled by `tama migrate`, not by the app silently migrating files).

2. **`migrate.rs` — `pub async fn run(opts: MigrateOpts) -> Result<MigrationReport>`:**
   - Open SQLite READ-ONLY (`Connection::open`, then `PRAGMA query_only = ON`) — the tool never writes it; test asserts the file's bytes are unchanged before/after.
   - Read `PRAGMA user_version`; < 49 → refuse ("upgrade the v2 binary first").

   - **Refuse if target has data** (`SELECT count(*)` on `model_configs`, `api_keys`, `app_general` — nonzero → bail) or if the bootstrap `config.toml` already exists — unless `--force`.

   - **Real run — ONE sqlx transaction:**
     - Table order: a **conservative parents-first convention** (config singletons → model_configs → model_files → model_aliases → provider tables → api_keys → pull queue → tamad → benchmarks/suite history → installations → system_metrics_history → active model/registry).      - Per table: `SELECT * ... ORDER BY id` from SQLite; batched parameterized inserts into Postgres with explicit `id` values (allowed by `BY DEFAULT` identity) and `ON CONFLICT (id) DO NOTHING` (idempotent re-runs under `--force`). **`logical_id`/`backend_id` columns are copied verbatim** (v2 rows already carry them; the deleted `backfill_backend_logical_ids` is legacy repair, not a source of values).
