# Log store in embedded SQLite, not the Postgres app DB

Tama stores structured tracing events (proxy, tamad, and engine logs) in an embedded SQLite database under `base_dir/logs/tama-logs.db` (table `logs`), not in the Postgres application DB. **Durability class drives storage choice:** the app DB holds durable app state (config, models, registry) that must survive reinstalls and is the `pg_dump` backup target; logs are ephemeral operational data — a bounded debugging window (defaults 7d / 50k rows / 256 MB, all configurable) that is read and discarded, never backed up. SQLite keeps logs physically separate from app state — one portable file, openable with `sqlite3` while the proxy or Postgres is down (exactly when you most need the logs), no ephemeral rows polluting `pg_dump` — and makes the write path simpler and faster: a single dedicated writer connection on `rusqlite` in WAL mode instead of TLS network round-trips through the shared bounded Postgres pool.

## Considered Options

- **`logs` table in Postgres** (jsonb/text + `pg_trgm` GIN + `(level, ts)` B-tree) — the initial research recommendation, on operational grounds ("Postgres is already a hard startup dependency, so a second store's marginal ops cost is zero"). Rejected on discussion: it mixes ephemeral data into the durable store, its only advantage ("if PG is down, Tama is already down") is the *wrong* failure direction for logs — during a PG problem the logs are the thing you most need to read — and putting ephemeral rows into `pg_dump` is a cost, not a benefit.
- **Embedded SQLite + FTS5** — chosen. Forced consequence: the retention pruner must run `PRAGMA incremental_vacuum(n)` inside the delete loop; without it the file grows monotonically (known failure mode, e.g. openai/codex#35823).
